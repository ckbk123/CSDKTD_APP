# Interface refinement after exercise completion

The human wants the accepted bounded functionality finished first, followed by small interface iterations informed by trying the tools together. The current draft asks students to absorb too much setup before seeing the concept. This record identifies presentation follow-ups; it does **not** assign a redesign, authorize changes to other modules, or replace mathematical acceptance and the remaining TASK requirements. Current ownership and delivery gates remain in [RESUMED_COORDINATION.md](RESUMED_COORDINATION.md).

## Intended student workflow

1. **Start with a useful baseline visual.** Open on valid default data, a concrete question, and a computed diagram/plot or concise initial preview. Label a preview and a checked answer distinctly. A prediction exercise need not expose its answer to provide orientation.
2. **Keep the primary controls beside the visual.** Show the few variables needed for the first experiment, with readable equations, units and an immediate explanation of their effect. Leave the complete supported model editable through optional controls.
3. **Offer one meaningful experiment and a clear action.** A student should be able to change a parameter, make a prediction, and calculate/check/reveal its consequence without configuring a general-purpose solver first. Keep draft changes and the last checked model unambiguous.
4. **Make depth optional, not absent.** Put full derivations, coefficient tables, alternative input methods, advanced settings and detailed numerical limits in clearly labeled expandable sections. Retain intermediate reasoning required by the exercise.
5. **Show mathematical warnings immediately.** Invalid or stale input, instability, singularities, unresolved numerical work, insufficient horizons and assumptions affecting interpretation belong beside the relevant control or visual. Do not bury them in collapsed diagnostics or leave a previous successful plot looking current.

Preserve each module's TASK, bounded solver scope, independent mathematical checks and numerical qualifications. Simplification must not remove required modes, changed-data experiments, input alternatives or honest failures. Preserve visual equation entry, keyboard alternatives, scoped styles, independent per-visit state, and the existing synchronous mount/abort/cleanup/reset contract. This plan does not introduce shared mutable models, a framework, a new shell, persistence, dependencies or deployment work.
